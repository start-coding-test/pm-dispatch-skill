# 验收手法手册

这份是 PM 验收现场照做的操作手册。SKILL.md 讲流程，这里讲**怎么判**——
每一条都对应一次真实返工或一次真实漏判。

## 0. 总原则：不读结论，重跑命令

执行者的结果文件只用来做两件事：**定位要重跑什么**、**看他声称的事实是否可复核**。
凡是"我跑了 X，输出是 Y"，一律自己再跑一遍。判定只认自己看到的输出与退出码。

## 1. 三查的具体形态

| 查什么 | 怎么做 | 漏掉的代价 |
|---|---|---|
| 存在性 | Glob/Read `work/Txx/`，比行数、比大小，不看结果文件自述 | 产物根本没落地 |
| 可复现 | PM 亲自重跑卡 §8 每条命令，取**尾部汇总 + 退出码** | 局部片段绿被当成全绿 |
| 逐条对照 | 卡内验收项一条条打勾，缺一条就是缺一条 | "主流程能跑"掩盖边缘项 |
| 没变松 | `scripts/audit-assertions.cjs`（见 §2） | 回归被静默删掉 |
| 不是恒真 | `scripts/mutate-check.cjs`（见 §3） | **最贵的一条**：断言全绿但什么都不判 |
| 引用可核对 | 取证卡的 `文件:行号` 随机抽 ≥5 条打开对原文 | 报告是编的 |

## 2. 回归没有变松 —— 机械核对，不要靠读 diff

人眼读 diff 判断"有没有删断言"会漏，尤其当断言被改名、被挪进循环时。做法：
把**改动前版本**里每条断言/测试的标题抽出来，逐条到**当前版本**里找。

```
node "$S/scripts/mutate-check.cjs" ...        # 见 §3
node "$S/scripts/audit-assertions.cjs" <仓库绝对路径> <相对文件路径> [--ref HEAD] [--preset check]
```

判读规则：

- **消失的标题必须逐条有名有姓**，并能在新代码里找到对应新标题（改名是允许的，删掉不行）。
- 因删除某个功能而必然消失的断言，要在结果文件里点名"这条随功能一起删了"。没点名 = 可疑。
- 静态标题数 ≠ 运行时断言数（循环里的断言会跑多次）。**两个都要**：静态数用于核对覆盖，运行时数用于设下限。
  下限写"上一轮实测的运行数"，不写静态数。

## 3. 断言不是恒真 —— 变异抽查

这是整个流程里性价比最高的一招：**把被测代码改坏一个点，看断言会不会红**。不红说明那条断言没在判定。

```
# plan 文件（绝对路径，JSON）：
{
  "repo": "D:/proj",
  "files": ["src/parser.js", "src/rules.js"],
  "cases": [
    { "id": "M1", "file": "src/parser.js", "from": "if (c.startsWith(\"92\")) return 30;", "to": "", "cmd": "node tests/unit.mjs" },
    { "id": "M2", "file": "src/rules.js",  "from": "price >= upPrice - 1e-6", "to": "false", "cmd": "node tests/unit.mjs" }
  ]
}
```
```
node "$S/scripts/mutate-check.cjs" --plan "D:\\proj\\temp\\mutate-plan.json" --baseline
```

要点：

- **一次只改一个点**，多处同时改会让红点归因不了。
- 每个变异点应该杀掉**具体哪几条**断言要能说出来；杀不掉的那条断言是装饰。
- 变异必须在**副本/可还原**的前提下做，脚本结束要把文件还原并**逐字节校验**；
  未跟踪的新文件不能靠 `git checkout` 还原（会丢），所以驱动里自带备份。
- 现场跑不了离线套件时（GUI/权限被拦），变异抽查照样能做——它是纯离线手段，别放弃这一招。

## 4. 现场红的分类法：先判"是哪一类红"

拿到一串红，先分类再决定打回谁：

| 类型 | 特征 | 处置 |
|---|---|---|
| **代码红** | 断言判据成立、被测行为错 | 打回执行卡 |
| **断言红** | 判据写错（把产品既有文案当 bug、把不可实现的措辞写死） | 打回，并**回改卡片里那条判据** |
| **判定输入红** | 判据本身对，但它读错了输入（例如把"默认/注册表首位"当成"当前实际值"） | 打回，指到具体参数/行 |
| **环境红** | 外部依赖可用性/时段/网络状态变了，代码与断言都没错 | **不打回**；把这条基线标为暂不可用，另开卡做状态无关化 |
| **时序红** | 固定 `sleep` 赌异步、元素没等到就操作 | 打回，硬性要求 `waitUntil` + 缺元素产出可读 FAIL |

现场红必须在**同一环境下重跑第二次**才归因：一次 3 红、一次 5 红，本身就说明输入在漂，
那种"稳定性差异"往往就是判据依赖了运行时的浮动量。

## 5. 打回卡 §10 怎么写

四段，缺一不可：

1. **实测原样**：命令、尾部汇总、FAIL 行与紧邻其上的诊断行（`r.info`/log）。带**时间戳**，两次运行就贴两次。
2. **根因定位**：精确到"哪个参数传错了 / 哪一行的假设不成立"，并指出**证据就在对方自己的产出里**——
   这种打回对方无法狡辩，也最容易一次修对。
   （实例形状：同一轮里 `· 出网预算: 实测 1 次`（绿）和 `· 源判定: …没有失败记录，却用了非首选源`（红）并存，
   说明判定读错了"首选"的来源，而真正的答案在插件自己回显的字段里。）
3. **逐条问题的定性**：是代码错、断言错、还是卡片措辞不可实现。**卡片措辞错要写明显是 PM 的错**，
   否则下一轮对方会照着错误的措辞再产出一版恒红断言。
4. **放行条件**：编号列出、每条都可机械复跑（含"必须实测一次某时刻的现场"这种硬条件）。
   明确禁止的省事路径（"不许简单把上限调大凑绿""不许删断言""不许把判据整条撤掉"）。

打回后：结果文件改名 `Txx.md.retry1`，**卡片正文里错的"事实"同时改掉**，台账记一句"谁纠正了谁"。

## 6. 统合阶段的坑

- 收拢产物时改了 import 路径/文件名 → **必须复跑**，并 diff 核对"只改了这几行"。
- 多卡串行同工作树时，`git diff --name-only` 是混合的。验收按**两卡白名单的并集**核对，
  然后**分包提交**；被打回卡的改动留在工作树不提交。
- 未放行的能力不要写进面向用户的文档（README/能力表）。代码没到，文档先到，下一个人会以为已经能用。
- 提交前 `git status` 复核：有没有把别人的未提交改动、临时探针目录、凭据类文件一起带进去。

## 7. 一句话自检清单（每次验收前扫一遍）

- [ ] 我重跑了吗，还是读了他的报告？
- [ ] 断言标题做过机械核对吗？
- [ ] 变异抽查跑了吗，有几个点？都杀掉了几个？
- [ ] 红点分类清楚了吗（代码红/断言红/输入红/环境红/时序红）？
- [ ] 现场红在**同一环境**重跑过第二次吗？
- [ ] 卡片里那条判据本身可实现吗？是不是我写错了？
- [ ] 没复跑的项，写进台账「PM 未复跑」了吗？
